# Family Assistant

Telegram-бот для семейного планирования. Принимает задачи обычными
фразами на русском, напоминает о них и присылает сводки.

```
«Севе теннис во вторник в 3»  →  Принял: Сева — теннис, ВТ 15:00
```

Понимает не только разовые дела, но и уклад недели:

```
«домашка понедельник среда четверг Севе и Глебу в 17:00»
→ Принял: Сева — домашка, ПН СР ЧТ 17:00  (каждую неделю)
→ Принял: Глеб — домашка, ПН СР ЧТ 17:00  (каждую неделю)
```

## Команды

Фиксированные строки, обрабатываются в `handle.py` ДО вызова парсера:
мгновенно, без обращения к API и без риска, что модель примет запрос
за новую задачу.

| Команда | Что показывает |
|---|---|
| Сводка на день | то же, что утренняя сводка в 08:00 |
| Сводка на неделю | 7 дней вперёд, сгруппировано по дням |
| Сводка на месяц | 30 дней вперёд |
| Сводка вся | месяц по дням + всё дальше + отдельные дела + привычки |
| Список дел | задачи без даты (`backlog`) |
| Ежедневные | привычки, с отметкой «сделал» и кнопкой удаления |
| Правила | расписания недели, с паузой и удалением |
| Инструкция | короткая справка для тех, кто в чате впервые |

Текст справки живёт в `build_help()` и отдаётся также по `/start` —
один источник на двоих, иначе они разойдутся.

Синонимы каждой команды — в словаре `COMMANDS`, около шестидесяти форм.
Сравнение по полной строке после нормализации: регистр, лишние пробелы
и точка в конце не важны, ведущие глаголы отбрасываются.

Список ведущих глаголов `LEAD_VERBS` проверяется по порядку и
останавливается на первом совпадении, поэтому длинные варианты стоят
первыми: иначе от «дай мне инструкцию» осталось бы «мне инструкцию».

Ведущее «сводку» приводится к «сводка» отдельным правилом: после
отбрасывания глагола остаётся винительный падеж, а в таблице ключи
в именительном. Одно правило вместо второй копии всех форм.

«Сводка на день» — команда. «Записать сводку на день по проекту» —
задача.

## Структура

```
app/
  db.py          весь SQL проекта, больше нигде его нет
  parser.py      фраза → структура (Claude Haiku, tool use)
  handle.py      что делать с разобранной фразой + команды
  ui.py          вёрстка сообщений и кнопки
  scheduler.py   когда и что отправлять
  bot.py         Telegram: приём сообщений и нажатий
db/
  schema.sql     6 таблиц, ENUM-типы, CHECK-ограничения
  migrate.py     накатывание миграций
  migrations/    нумерованные файлы миграций
parser/
  parser_prompt.md    промпт со всеми правилами разбора
  eval_dataset.json   31 фраза с эталонным разбором
  run_eval.py         прогон, точность, стоимость
tests/
  test_weekdays.py    правила, работающие ПОСЛЕ парсера
```

Слои изолированы: `bot.py` не знает про SQL, `db.py` не знает про
Telegram. Когда что-то ломается, это сужает область поиска.

## Запуск

```bash
pip3 install -r requirements.txt
createdb familybot
psql -d familybot -f db/schema.sql

python3 app/bot.py          # тестовый бот
python3 app/bot.py --prod   # рабочий
```

Настройки в `.env` в корне (в git не попадает):

```
ANTHROPIC_API_KEY=sk-ant-...
DATABASE_URL=postgresql://пользователь@localhost/familybot
TELEGRAM_TOKEN_DEV=...
TELEGRAM_TOKEN_PROD=...
TELEGRAM_CHAT_ID_DEV=-100...
TELEGRAM_CHAT_ID_PROD=-100...
```

## Проверки

Три разных жанра, каждый проверяет свой слой.

```bash
python3 parser/run_eval.py --runs 3   # модель: точность разбора фразы
python3 tests/test_weekdays.py        # код между парсером и базой
python3 app/db.py                     # слой БД + CHECK-ограничения
```

`run_eval.py` смотрит, что модель вернула на фразу. `tests/` проверяет
правила, которые правят её ответ уже после разбора — eval их не видит
вовсе. `app/db.py` заводит тестовые данные и проверяет, что база
отвергает недопустимое.

Разовые проверки:

```bash
python3 app/parser.py "фраза"          # разбор одной фразы
python3 app/handle.py "фраза"          # разбор + запись в базу
python3 app/scheduler.py morning       # сводка вне расписания
python3 app/scheduler.py expand        # развёртка правил вручную
```

## Модель времени

Пять режимов, от точного к бессрочному:

| режим | пример | напоминает |
|---|---|---|
| `exact` | «теннис в 15:00» | лестница ступеней |
| `range` | «с 15 до 17» | лестница от начала |
| `daypart` | «прописи утром» | один раз в начале окна |
| `allday` | «в среду цемент» | только в сводке |
| `undated` | «надо газон» | никогда |

Активные часы 06:00–23:00. Утро 07–12, день 12–17, вечер 17–21.

Часы 1–7 без уточнения читаются как дневные («в 3» → 15:00), 8–11
вызывают переспрос: обе трактовки попадают в активное окно.

Двоеточие и точка — разделители времени, а не даты. `6:30` и `6.30`
одинаково дают 18:30. Точка разбирается по трём шагам: день уже назван
словом → это время; одна из трактовок невозможна (`25.09` — часа 25
не бывает) → берётся возможная; обе возможны и дня нет → переспрос.

Даты семья пишет словами: «в четверг», «15 сентября».

Часы 8–11 разрешаются автоматически, если во фразе есть «утром»,
«днём», «вечером» или «ночью». Это делает не промпт, а `handle.py`:
получив переспрос про две трактовки одного времени, код сам выбирает
половину суток и прогоняет фразу повторно. Человек кнопок не видит.
Цена — второй вызов API в таких фразах.

## Лестница напоминаний

Задача с точным временем получает четыре напоминания:

| Момент | Текст | Кнопки |
|---|---|---|
| −60 мин | `⏰ через 1 час: Сева — теннис (15:00)` | нет |
| −30 мин | `⏰ через 30 минут: …` | нет |
| −10 мин | `⏰ через 10 минут: …` | нет |
| начало | `🔔 сейчас: Сева — теннис (15:00)` | ✅ и ⏰ |

Значок у последней ступени другой намеренно: только под ней есть
кнопки, и это должно быть видно глазом до нажатия.

**Текст привязан к ступени, а не к разнице во времени.** Раньше
считался из разницы: планировщик просыпался внутри окна на несколько
десятков секунд позже ровной отметки, остаток округлялся вниз, и вместо
«через 10 минут» приходило «через 9 минут».

**Кнопки только в момент начала.** До события отмечать «сделано»
нечего, а случайное нажатие закрывает задачу молча: напоминаний больше
не придёт, и человек узнает об этом, когда событие уже прошло.

**Каждая ступень — свой вид в `reminder_kind`.** Защита от дублей стоит
на ключе `(task_id, kind, sent_date)`: под общим `timed` вторая ступень
того же дня не прошла бы.

**Проверка раз в минуту.** При пятиминутном опросе ступень пришлось бы
ловить окном той же ширины, и «через 30 минут» гуляло бы на пять минут
в обе стороны. Запрос идёт по частичному индексу и стоит копейки.

**Пропущенная ступень не догоняется.** Если бот был выключен всё окно,
напоминание не придёт вовсе: написать «через час» за сорок минут хуже,
чем промолчать, а следующая ступень всё равно придёт. То же с ночной
тишиной — событие в 06:30 не получит часовую ступень.

Привычки со временем тоже напоминают: у них `date` равен `NULL`,
поэтому в выборках стоит отдельная ветка `OR list = 'daily'`.
Дедупликация посуточная, так что привычка получает свой набор ступеней
каждый день.

## Правила недели

Расписание живёт в `task_templates`, а не в `tasks`. Одна строка —
одно правило: «домашка, Сева, дни {0,2,3}, 17:00». Даты у правила нет,
есть набор дней недели.

Раз в сутки в 03:30 развёртка создаёт из правил обычные задачи на две
недели вперёд. Поэтому расписание не кончается: горизонт всё время
отодвигается. Развёртка идёт ещё в двух случаях — при старте бота
(если процесс простоял сутки, задачи на сегодня нужны сразу) и сразу
после создания правила фразой.

**Развёртка идемпотентна.** Уникальный индекс `(template_id, date)`
не даёт создать дубль, `ON CONFLICT DO NOTHING` гасит повтор. На этом
держатся и ночное задание, и прогон при старте: одну и ту же дату
развёртка видит десятки раз.

Индекс намеренно не частичный: у обычных задач `template_id` равен
`NULL`, а `NULL` в уникальном индексе не конфликтует сам с собой. Зато
`ON CONFLICT` на полном индексе выводится однозначно, а с частичным
Postgres потребовал бы повторять предикат.

### Когда фраза становится правилом

Три признака, любого достаточно:

- **названо три дня и больше.** «Понедельник, среда, четверг» — никто
  не перечисляет три дня ради одного раза;
- **есть слово повтора:** «каждый вторник», «по средам», «еженедельно».
  Тогда хватает одного дня;
- **парсер поставил `recurring`.** Раньше это поле приходило
  и выбрасывалось: бот показывал «(каждую неделю)» и ничего
  не повторял.

Не правило, если во фразе явная дата словами («в четверг 17 сентября»)
или слово сдвига («в среду через неделю») — это про конкретный раз.
Задачи без даты не рассматриваются вовсе.

Порог в три дня человеку не виден, поэтому подтверждение его
проговаривает пометкой «(каждую неделю)». Без неё непонятно, почему
«среда и пятница» дали разовые дела, а «среда, пятница, суббота» —
расписание.

**У двух дней исход зависит от модели.** «В среду и пятницу» без слова
«каждый» станет правилом, только если парсер сам поставил `recurring`.
Слово «каждый» делает результат однозначным при любом её решении.

### Одно правило на человека

Модель часто сама раскладывает фразу по дням: «домашка ПН СР ЧТ Севе
и Глебу» приходит шестью задачами, а не двумя. Правило описывает все дни
сразу, поэтому шесть правил означали бы шесть расписаний и шесть
напоминаний на каждый день. `_rule_subjects()` оставляет по одному
на сочетание названия и человека.

Та же защита, что при размножении разовых задач по дням, только с другой
стороны: там она мешает умножить уже разложенное, здесь — завести
лишние правила.

### Повтор фразы правит, а не дублирует

Поиск по паре название плюс человек — именно её называет человек, а дни
и время при повторе как раз могут отличаться. Нашлось активное правило
— оно обновляется, и подтверждение говорит «Обновил» вместо «Принял».

Это заодно единственный способ изменить расписание словами. Но новая
фраза сама должна быть распознана как расписание: сжать правило
до двух дней получится только со словом «каждый» или «по вторникам».

### Что происходит с задачами при изменениях

**Правка правила** удаляет незакрытые экземпляры от сегодня, развёртка
создаёт новые. Иначе смена «ПН СР ЧТ» на «ПН ВТ» оставила бы четверги
висеть.

**Пауза и удаление** тоже убирают незакрытые экземпляры от сегодня.
Иначе правило перестало действовать, а задачи на эту неделю остались бы
— и понять почему было бы нельзя.

**Прошедшие задачи не трогаются никогда.** «Домашка была в среду
и сделана» остаётся правдой, даже если расписание потом отменили.
Это история, а не план.

Пауза отдельно от удаления: каникулы и отпуск — не повод терять
расписание, которое потом набирать заново. Приостановленные правила
показываются в списке отдельным блоком с кнопкой возврата.

## Привычки и галочка

Привычка — одна строка в `tasks` с `list = 'daily'` и без даты.
Она и правило, и экземпляр.

Отметка «сделал сегодня» **ничего не записывает в базу.** Это
мотиватор: нажал и видишь галочку. Ни статуса, ни истории, ни влияния
на просрочку — привычка остаётся `pending` и придёт завтра как обычно.

Поэтому состояние отметки живёт в самой клавиатуре: отмеченная кнопка
нарисована с ✅ и пустым действием, а `bot.py` собирает набор
отмеченных, читая подписи кнопок. Хранить негде — сообщение и есть
хранилище.

Цена решения: отметки живут до перерисовки сообщения. Вызвал
«ежедневные» заново — пришло новое сообщение с чистыми галочками.
Иначе пришлось бы писать в базу, то есть делать то, от чего отказались
сознательно.

Переноса у привычек нет: «перенести зарядку на завтра» ничего
не значит, завтрашняя всё равно придёт.

## Задачи за горизонтом

Сводки смотрят на 7 и 30 дней. Задача на декабрь не была видна нигде
до самого декабря: записал и проверить нельзя, через месяц не помнишь,
записывал ли, и записываешь заново.

Теперь два места.

Периодические сводки в конце сообщают, что за горизонтом что-то есть,
и говорят, где смотреть: «После 11 октября ещё 3 задачи — смотри
„сводка вся“». Если за горизонтом пусто, строки нет.

Общая сводка показывает всё блоком «📆 Дальше», без потолка по датам.
Для другого года дата выводится с годом: без него «01.03» непонятно —
это следующий март или уже прошедший.

## Решения, зафиксированные при проектировании

**Расписание считает код, не модель.** LLM разбирает язык на входе.
Когда слать напоминание — детерминированная работа.

**Всё время в UTC, показывается в Europe/Dublin.** Ирландия переводит
часы дважды в год.

**Ежедневные задачи не переносятся.** Не сделал — сгорело, без вопросов
и без попадания в отдельные дела.

**Просроченные не переезжают сами.** Автоперенос скрыл бы факт, что
дело не сделано, и `postponed_count` перестал бы что-либо значить.

**Разметка HTML, не Markdown.** Одиночное подчёркивание или звёздочка
в тексте задачи ломает отправку в Markdown целиком.

**Бот не знает, кто пишет.** Общий чат, общая база, без прав.

**Номер задачи не показывается.** Это `id` из базы: растёт без конца
и не переиспользуется, через год в каждой строке были бы пятизначные
числа. Человеку он не нужен — закрытие и перенос идут кнопками или
фразой, а нужную строку парсер находит сам по списку открытых задач.

**Имя исполнителя пустое у общих дел.** Раньше выводилось «дом»:
строка «дом — косить траву» ничего не добавляет к «косить траву», а
в сводке из десяти дел половина начиналась одинаково.

**Механические правила — в код, модели остаётся язык.** Разрешение
часа по слову «утром» три раза пытались вписать в промпт: каждый раз
ломались соседние правила, точность падала до 94% и появлялась
нестабильность. Тридцать строк в `handle.py` решили то же самое без
единой регрессии.

Промпт держит около 350 строк правил, и каждое новое конкурирует
с прежними за внимание модели. Если правило можно записать условием
и таблицей — ему место в коде.

**Правило может быть в промпте, верным, и всё равно не работать.**
9 сентября фраза «Вова Четверг сходить к ветеринару в 4.30» дала
17 сентября вместо 10-го. Правило «следующее наступление, исключая
сегодня» в промпте было и сформулировано верно — модель его нарушила.
Починка ушла в код: `_fix_weekday_date()` не считает дату за модель,
а проверяет её ответ и сдвигает только тогда, когда день недели совпал,
а неделя выбрана не та.

**Поведение модели может зависеть от контекста, а не от правил.**
Перечисление дней недели давало то восемь задач, то две — в одном
контексте одно, в другом другое, три прогона подряд стабильно каждый
раз. Прогон eval это и поймал, 0 из 3. Размножение по дням ушло в код.

**Не всякое поведение стоит закреплять кейсом.** Кейс на перечисление
дней из датасета убран: эталон для такой фразы не выводится из правил
— сколько задач определено, а какая у них дата при четырёх названных
днях нет. Проверять неопределённое поведение значит завести кейс,
который однажды сломается сам. Вместо него проверка в `tests/`.

**Ответ на переспрос заменяет, а не дополняет.** Выбранный вариант
приходит отдельной строкой «Уточнение: …». Раньше он клеился через
тире, и «пилатес в 9 — 21:00» превращалось в диапазон 09:00–21:00.

**Правка сообщения не разбирается, но и не игнорируется.** Telegram
шлёт её отдельным полем `edited_message`. Разобрать как новую фразу
нельзя — вышел бы дубль, а связи `message_id` → `task_id` в базе нет.
Бот отвечает, что правку не видит, и просит написать заново.
Молчание было хуже: человек думал, что бот перечитал текст.

**Вариант переспроса сначала проверяется как команда.** Иначе
«Посмотреть список дел» уходило обратно в парсер и вызывало тот же
переспрос по кругу.

**Правка сообщения на то же самое — не ошибка.** Telegram отвечает
`BadRequest: Message is not modified`. Для нас это норма: перерисовка
сводки после нажатия ✅ на уже закрытой задаче даёт тот же текст,
и убрать клавиатуру, которой нет, — тоже. `_safe_edit()` гасит только
эту ошибку и пробрасывает все остальные: глушить их скопом — верный
способ спрятать настоящую поломку.

## Точность парсера

Haiku 4.5, `temperature=0`: 31/31 на eval-датасете, три прогона подряд
без разброса. Около $0.61 за 300 сообщений при кешировании промпта.

Датасет пополняется реальными ошибками из `message_log`, а не
придуманными фразами. Исходные 22 кейса не удаляются — это
регрессионная база.

Опорная дата датасета `2026-09-03` (четверг) зафиксирована ради
воспроизводимости. Менять её нельзя — поедут все ожидаемые даты.
Важное следствие: проверка через `app/parser.py` идёт при сегодняшней
дате и с открытыми задачами из базы, а eval — при опорной и без них.
Поведение модели может отличаться, и это уже ловилось.

## Миграции

Схема в `db/schema.sql` описывает базу целиком и работает только при
установке с нуля. Живую базу меняют файлы в `db/migrations/`.

```bash
python3 db/migrate.py --status    # что применено, что ждёт
python3 db/migrate.py --dry-run   # план, ничего не выполняя
python3 db/migrate.py             # накатить
```

Журнал применённого — таблица `schema_migrations`, ключ по имени файла.
Повторный запуск ничего не делает. Переименовывать применённый файл
нельзя: под новым именем он накатится второй раз.

Имена: `001_reminder_stages.sql`, `002_template_expansion.sql` —
трёхзначный номер, потом короткое имя. Сортировка по алфавиту совпадает
с порядком применения.

**Транзакции.** По умолчанию файл выполняется через `psql -1`, то есть
целиком или никак. Но `ALTER TYPE ... ADD VALUE` внутри транзакции
не работает: до PostgreSQL 12 запрещён вовсе, а начиная с 12-й
добавленное значение нельзя использовать до конца транзакции. Такому
файлу нужен автокоммит, и он объявляет это первой строкой:

```sql
-- no-transaction
```

Плата: упавший на середине файл оставит часть команд закоммиченной,
а миграцию незаписанной. Поэтому такие файлы пишутся идемпотентно —
`IF NOT EXISTS` и подобное.

## Что не сделано

- **закреплённый план недели.** Таблица `pinned_plan` есть, кода нет:
  сводка отправляется обычным сообщением, в чате не закрепляется
- **паузы на человека и на всю систему.** Таблица `pauses` есть
  и учитывается во всех выборках через `_NOT_PAUSED`, но завести паузу
  из чата нельзя. Пауза отдельного правила работает кнопкой
- **еженедельный разбор паттернов** по истории
- **статистики привычек нет** по устройству: отметка «сделал» ничего
  не записывает. Если понадобится «сколько дней подряд» — потребуется
  таблица отметок по датам
- **правило меняется только полной фразой.** Нет ни команды словами,
  ни кнопки «изменить»: только пауза и удаление

## Работа с сервером

Сервер: Oracle Cloud, Ampere A1 Flex (1 OCPU, 6 ГБ), Oracle Linux 9,
регион Paris, пользователь `opc`. Аккаунт в пределах Always Free —
лимит с 15 июня 2026 составляет 2 OCPU и 12 ГБ на весь тенант, форма
укладывается с запасом вдвое.

Бот работает как systemd-служба `familybot`, автозапуск включён.

```bash
ssh opc@158.178.213.121

systemctl status familybot         # состояние службы
sudo systemctl restart familybot   # перезапуск после git pull
sudo systemctl stop familybot      # остановить
journalctl -u familybot -f         # логи в реальном времени, выход Ctrl+C
```

Юнит: `/etc/systemd/system/familybot.service`
После правки юнита — `sudo systemctl daemon-reload`, затем `restart`.

Обновление без изменений схемы: `git pull`, затем `restart`. Код
и промпт читаются один раз при старте, без перезапуска изменения
не подхватятся.

Если в обновлении есть миграция, порядок жёсткий:

```bash
cd family-bot
git pull
pg_dump familybot > ~/backup_$(date +%Y%m%d).sql
python3 db/migrate.py
sudo systemctl restart familybot
```

Сначала миграция, потом рестарт. Наоборот нельзя: новый код полезет
в колонки, которых ещё нет.

Строка расписания в логе при старте показывает, что именно встало:

```bash
journalctl -u familybot -n 25 --no-pager -o cat | grep расписание
```

Ожидается упоминание сводок 08:00 и 21:00, проверки задач каждые
60 секунд, ступеней 60, 30, 10, 0 и развёртки правил в 03:30.

### Базы на сервере

| База | Назначение |
|---|---|
| `familybot` | боевая, с ней работает служба |
| `familybot_dev` | пустая, для экспериментов |

Переключение — правка `DATABASE_URL` в `.env` и перезапуск службы.

Локальная база на Mac отдельная от серверной: задачи из тестов в чате
не появятся. Миграции надо накатывать на обе.

### Грабли

**`localhost` в `DATABASE_URL` не работает.** libpq трактует его как
TCP-подключение, а `pg_hba.conf` в Oracle Linux требует для TCP
ident-аутентификацию, которой на сервере нет. Правильно:
`postgresql:///familybot` — пустой хост означает Unix-сокет
и метод peer.

**SSH рвётся на долгих операциях.** В `~/.ssh/config` на Mac:

    Host 158.178.213.121
        ServerAliveInterval 60

Директивы `ServerAliveExitOnFailure` не существует — ssh откажется
читать весь конфиг.

**Команды после `ssh` набирать по одной.** Если набрать пачкой, пока
соединение поднимается, ввод уходит в буфер и выполняется где попало —
чаще всего на Mac вместо сервера. Ловилось много раз, в том числе
с прогоном eval на сервере вместо Mac (потраченные $0.19 и результат
по старому датасету) и с `git push`, попросившим логин к GitHub.

Надёжное средство: держать две вкладки терминала — в одной только
сервер, в другой только Mac. Тогда `cd ~/Desktop/...` физически некуда
улететь.

**Права на конфиги.** `.env` и `~/.ssh/config` должны быть `chmod 600`,
иначе ssh игнорирует конфиг, а ключи доступны на чтение другим
пользователям.

**Бесплатные инстансы Oracle забирает за простой.** Если процессор
и сеть почти не нагружены неделю, машину могут освободить. Бот именно
такой — полторы секунды процессорного времени за два часа. Страховка:
`pg_dump` по расписанию и копия дампа не на самом сервере.
