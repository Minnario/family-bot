# Eval парсера Family Assistant

Проверка того, что модель правильно разбирает фразу. Только парсер:
правила, которые правят её ответ уже после разбора, живут в `handle.py`
и проверяются отдельно — `python3 tests/test_weekdays.py`.

## Запуск

```bash
python3 parser/run_eval.py --runs 3     # рабочая проверка
```

Три прогона обязательны: один не покажет нестабильность, а именно она
и была главной проблемой при правках промпта.

Остальные флаги:

```bash
python3 parser/run_eval.py                   # один прогон, haiku
python3 parser/run_eval.py --model all       # сравнить три модели
python3 parser/run_eval.py --verbose         # показать разбор каждого кейса
```

Модель по умолчанию `haiku` — та, что стоит в проде. `sonnet` и `opus`
есть в `MODELS` для сравнения цены и точности, но в боте не
используются.

Нужен `ANTHROPIC_API_KEY` в `.env` в корне проекта.

## Файлы

| Файл | Что это |
|---|---|
| `parser_prompt.md`   | системный промпт, шаблон с `{{TODAY}}`, `{{WEEKDAY_RU}}`, `{{OPEN_TASKS}}` |
| `eval_dataset.json`  | 31 фраза с эталонным разбором |
| `run_eval.py`        | прогон, сравнение, точность и стоимость |

## Как читать вывод

```
Точность : 31/31  (100%)   [3 прогона]
Токены   : 46275 in / 14310 out
Кеш      : 6726 записано / 618792 прочитано  (попаданий 99%)
Стоимость: $0.1881  (~$0.61 за 300 сообщений)

нестабильных: 0
```

При расхождении печатается кейс и то, какое правило не сработало:

```
Расхождения (1):

  #5  Глеб тренировка по футболу 6:30, среда   [прошёл 0/3]
       проверяет: 6:30 с двоеточием → 18:30
       ✗ time_start: ждали '18:30', получили '06:30'
```

Строка `проверяет` берётся из поля `tests` кейса. `[прошёл 0/3]`
показывает нестабильность: 1/3 или 2/3 хуже, чем 0/3, — значит модель
плавает, и правка промпта не воспроизводима.

Правится промпт, не датасет.

Сравниваются поля из `TASK_FIELDS`: `title`, `assignee`, `list`, `date`,
`deadline`, `time_mode`, `time_start`, `time_end`, `daypart`,
`recurring`, `reminder_lead`. Плюс `action`, количество задач
и содержимое `clarification`.

Сравнение задач построчное и чувствительно к порядку: эталон и ответ
идут парами по индексу. Для кейсов с двумя задачами порядок должен
совпадать с порядком имён во фразе.

## Правила работы с датасетом

1. **Не удалять исходные 22 кейса** при расширении. Это регрессионная
   база.
2. **Не подгонять эталон под вывод модели.** Если модель разобрала
   иначе, а её вариант правильнее — сначала признать это осознанно,
   потом менять.
3. **Каждая реальная ошибка бота** добавляется сюда новым кейсом
   с правильным разбором. В поле `tests` стоит писать дату и суть:
   так сделано в кейсах 23 и 29.
4. **Не заводить кейс на неопределённое поведение.** Если эталон
   не выводится из правил промпта, кейс однажды сломается сам. Так был
   убран кейс на перечисление дней недели: сколько задач правило
   определяет, а какая у них дата при четырёх названных днях — нет.
   Такое проверяется в `tests/`, а не здесь.
5. Опорная дата `2026-09-03` (четверг) зафиксирована ради
   воспроизводимости. Менять её нельзя — поедут все ожидаемые даты.

## Важно про разные контексты

Eval и бот запускают модель по-разному, и результат может отличаться.

| | опорная дата | открытые задачи в промпте |
|---|---|---|
| `run_eval.py` | 2026-09-03, фиксированная | нет, кроме кейса 21 |
| `app/parser.py` | сегодняшняя | из базы, все открытые |
| бот в проде | сегодняшняя | из базы, все открытые |

Это уже ловилось: фраза с перечислением дней недели давала восемь задач
при запуске через `app/parser.py` и две в eval. Три прогона в каждом
контексте, результат стабильный внутри контекста и разный между ними.

Вывод: «проверил через `app/parser.py`, работает» не означает, что
пройдёт eval. И наоборот.

## Что покрыто

Пять режимов времени · разрешение 12-часового формата (`6:30` → 18:30,
`3:00` → 15:00, `7 часов` → 19:00) · дедлайн против даты · три списка
(scheduled / backlog / daily) · размножение задачи на два имени ·
`assignee: null` при отсутствии имени · разговорный шум («после
работы») · незнакомые слова («гелик») · объём вместо времени старта
(«2 часа учу») · перенос с сохранением времени · день недели, названный
в тот же день (+7) · точка как разделитель времени во всех трёх шагах
разбора · переспрос при неоднозначной точке · ответ на переспрос,
заменяющий час и отбрасывающий дату.

Кейсы 23 и 29 — реальные ошибки бота от 8 и 9 сентября 2026.

## Чего НЕ покрыто

Закрытие задач («купил цемент») · отмена и пауза · время вне активных
часов · опечатки и слитный ввод (`1930`) · перечисление дней недели
(намеренно, см. правило 4).

Специально: сначала цифра на базовых случаях, потом расширение.

## Замечание про max_tokens

Скрипт проверяет `stop_reason == "max_tokens"` и помечает такой кейс
отдельно. Обрезанный `tool_use` — тихий сбой: ответ приходит, но
неполный.

Потолок в `parser.py` — 2000 токенов, около семнадцати задач в одном
ответе. Фраза вроде «пять дней на четверых детей» в него не уложится
и даст `ParseError` с просьбой переформулировать — это лучше, чем
молча потерять половину задач.
